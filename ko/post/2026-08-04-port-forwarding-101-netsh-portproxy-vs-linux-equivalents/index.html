Port Forwarding 101: `Netsh Portproxy` vs Linux Equivalents

  • Tue, Aug 4, 2026
  • 읽는 시간 9분

임베디드 엔지니어쟁이들의 업에서 빼놓을 수 없는 건 실제 타겟 보드에서의 디버깅입니다. 호스트 환경에서 아무리 열심히 개발하고 테스트하더라도, 소프트웨어가 실제 하드웨어에서 제대로 동작하는지는 결국 타겟 보드에서 직접 확인할 수밖에 없습니다. 그 보드가 특정한 물리적 환경에 묶여 있을 때 - 제 경우에는 차량 환경이죠 - 일이 고달퍼지기 시작합니다. 차고나 주차장에 있는 차량에 설치되어 있는 보드를 그 환경에서 사용해야 한다면요. 차량 옆에 쪼그려 앉아서 보드를 디버깅하고, 코드를 수정하고, 다시 배포하고, 또 테스트하는 일은 보기보다 고됩니다. 여기서 게으름을 조금 피워보죠. 여분의 Windows laptop을 차량에 두고, 그 Laptop을 통해 제 Desk에서 보드에 원격으로 접근해 보기로 했습니다.

제 Windows 노트북은 두 네트워크 Comnay VPN Wifi(172.160.a.b)와 Board Ethernet(192.168.x.y)에 동시에 연결되어 있었습니다.

1. SSH Jump Host 사용

쉽게 접근해봅시다. Windows laptop에 SSH로 접속한 다음, 그 shell에서 다시 타겟 보드로 SSH하면 됩니다.

# My current host
ssh windows_account@172.160.a.b

# Windows machine
ssh board_account@192.168.x.y

물론 매번 이렇게 두 번씩 접속할 필요는 없습니다. ProxyJump를 이용하면 Windows laptop을 jump host로 사용할 수 있습니다. 클라이언트의 ~/.ssh/config에 다음과 같이 설정합니다.

Host windows-jump
    HostName 172.16.a.b
    User windows_account

Host target-board
    HostName 192.168.x.y
    User board_account
    ProxyJump windows-jump

이제 다음 명령만 실행하면 한 번에 보드에 다다를 수 있습니다.

ssh target-board

2. SSH Tunnel로 특정 Port 노출

저 혼자만 이 환경을 사용한다면 SSH Jump Host만으로도 충분합니다. 문제는 다른 엔지니어들도 같은 보드를 사용해야 할 때였습니다. ProxyJump를 사용하려면 결국 각각의 사용자가 중간 Windows laptop에 인증을 거쳐 로그인 해야 합니다. Windows laptop이 공용이면 상관없지만 제 경우에는 제 업무용 Windows laptop을 임시로 차량에 가져다 논 거라서 옆 자리 동료가 보드를 살펴보고 싶다고 하니까 꽤나 난감해졌습니다. 저는 자리에서 원격으로 보고 동료는 직접 가라고 할 수는 없잖아요. 그리고 이미 Windows laptop에 물리적으로 연결된 보드의 Ethernet라인을 뻬고 다시 붙이고 다시 되돌려놓고. 그래서 제 Windows laptop 계정을 공유하지 않고 단순히 Windows laptop을 중간 매개체로만 이용하는 방식을 적용하기 시작했습니다.

Windows에는 이미 OpenSSH client가 있었기 때문에 가장 먼저 SSH port forwarding을 이용해 보았습니다. Windows laptop에서 타겟 보드로 SSH session 하나를 열면서 local port forwarding을 설정합니다.

ssh -N `
    -L 172.16.a.b:2222:127.0.0.1:22 `
    root@192.168.x.y

-N은 remote shell을 실행하지 않고 SSH connection을 forwarding 용도로만 사용하겠다는 의미입니다. -L 172.16.a.b:2222:127.0.0.1:22은 Windows 노트북의 172.16.a.b:2222에서 connection을 받은 뒤, 이미 만들어진 SSH connection을 통해 remote 측의 127.0.0.1:22로 전달합니다. 이때 remote SSH server가 192.168.x.y의 타겟 보드이므로 결과적으로 구조는 다음과 같습니다.

Other Engineer
      |
      | ssh root@172.16.x.y -p 2222
      v
Windows laptop
172.16.x.y:2222
      |
      | SSH tunnel
      v
Target board
192.168.x.y:22

이제 사용자는 Windows 계정을 알 필요가 없습니다. 그냥 아래 명령어를 통해 한 번에 보드에 접근 가능합니다. SSH authentication도 Windows 계정이 아니라 최종적으로 타겟 보드의 sshd를 상대로 이루어집니다.

ssh board_account@172.16.a.b -p 2222

3. netsh interface portproxy로 Persistent Port Forwarding 구성

이 방법으로 첫 번째 문제는 해결됐습니다. 하지만 사용하다 보니 또 다른 불편함이 생깁니다. forwarding이 존재하려면 SSH session이 항상 살아 있어야 합니다. Laptop이 재부팅되거나 SSH process가 종료되면 tunnel도 사라집니다. 물론 Task Scheduler나 script 등을 이용해서 자동으로 session을 다시 만들 수도 있습니다. SSH session 자체를 background process나 scheduled task을 lifecycle형태로 관리하는 것도 가능합니다. 하지만 이건 배보다 배꼽이 커지고 있는 느낌이랄까요.

방법은 조금 더 복잡해지지만 그림은 조금 더 쉽게 그려봅시다. 별도의 SSH session을 계속 띄워 두는 대신 Windows 자체에 172.16.a.b:2222 -> 192.168.x.y:22라는 forwarding rule을 영구적인 network configuration으로 설정할 수 없을까요?

netsh interface portproxy는 Windows가 특정 IP와 TCP port에서 connection을 받은 뒤, 이를 다른 IP와 TCP port로 전달하도록 설정할 수 있는 기능입니다.

제가 원하는 구성은 다음과 같았습니다.

172.16.10.22:2222
       |
       | TCP proxy
       v
192.168.0.10:22

관리자 권한의 PowerShell이나 Command Prompt에서 다음과 같이 설정합니다.

netsh interface portproxy add v4tov4 `
    listenaddress=172.16.10.22 `
    listenport=2222 `
    connectaddress=192.168.0.10 `
    connectport=22

설정된 rule은 다음 명령으로 확인할 수 있습니다.

netsh interface portproxy show all
...
Listen on ipv4:             Connect to ipv4:
Address         Port        Address         Port
--------------- ----------  --------------- ----------
172.16.10.22    2222        192.168.0.10    22

사용자는 역시 다음 명령어를 통해 한 번에 보드에 다다를 수 있습니다. SSH Tunnel과 똑같이 SSH authentication Windows 계정이 아니라 최종적으로 타겟 보드의 sshd를 상대로 이루어집니다.

ssh root@172.16.10.22 -p 2222

Firewall

조금 더 살을 붙여보겠습니다. 제대로 위 기능을 이용하기 위해서는 Firewall설정을 해야 합니다.

먼저 Windows Firewall에서 다른 machine이 TCP 2222에 접근할 수 있어야 합니다.

New-NetFirewallRule `
    -DisplayName "Board SSH Port Proxy" `
    -Direction Inbound `
    -Protocol TCP `
    -LocalPort 2222 `
    -Action Allow

실제 Company 환경이라면 모든 source에서 접근할 수 있도록 열기보다 source subnet을 제한하는 것이 더 적절할 수 있습니다.

New-NetFirewallRule `
    -DisplayName "Board SSH Port Proxy" `
    -Direction Inbound `
    -Protocol TCP `
    -LocalPort 2222 `
    -RemoteAddress 172.16.0.0/16 `
    -Action Allow

처럼 범위를 제한할 수 있습니다.

Windows에서 Target까지의 Connectivity

또 하나 당연하지만 중요한 조건은 Windows 노트북 자체가 타겟에 접근할 수 있어야 한다는 것입니다.

Windows laptop
172.16.10.22
      |
      | board-facing Ethernet
      v
192.168.0.10:22

먼저 Windows에서 아래 명령어가 성공하는지 확인합니다.

Test-NetConnection 192.168.0.10 -Port 22

실패한다면 portproxy를 디버깅하기 전에 Ethernet interface와 routing부터 확인해야 합니다. 아래 명령어를 통해 Windows가 192.168.0.10으로 가는 traffic을 어느 interface로 보내는지 확인할 수 있습니다.

route print

Listen 상태 확인

설정 후 실제로 해당 port가 열려 있는지도 확인할 수 있습니다.

Get-NetTCPConnection -LocalPort 2222

or

netstat -ano | findstr :2222

4. netsh portproxy는 실제로 무엇을 하는가?

netsh portproxy에 대해서 조금 더 Deep dive를 해보겠습니다. Linux에서 흔히 사용하는 DNAT를 아시는 분이라면 DNAT과의 비교가 직관적으로 와 닿을 것 같습니다.

먼저 portproxy기능은 이름 그대로 이 기능은 일반적인 NAT forwarding과는 다릅니다. NAT rule이 아니라 특정 주소와 TCP port에서 listen하고 incoming TCP connection을 다른 endpoint로 forwarding하는 proxy rule로 동작합니다. 지원범위도 TCP로 제한적입니다.

개념적으로는:

Client
   |
   | TCP
   v
+--------------+
| Windows Host |
| Portproxy    |
+--------------+
   |
   | TCP
   v
Target

와 같이 이해하는 편이 좋습니다.

제 환경에 대입하면:

Client
   |
   | TCP connection
   | 172.16.10.22:2222
   v
Windows laptop
   |
   | portproxy
   v
Target board
192.168.0.10:22

입니다.

여기서 중요한 것은 Windows 머신을 일반적인 IP router로 구성하는 것과는 다르다는 점입니다.

제가 특정 TCP service 하나를 외부에 노출하고 싶었을 뿐이지:

172.16.x.x network
        |
        | route every packet
        v
192.168.x.x network

처럼 두 subnet 전체를 routing하려던 것은 아니었습니다.

따라서 이 use case에서는 별도의 Layer-3 routing 환경을 구축하지 않고도 원하는 SSH port 하나만 선택적으로 proxy할 수 있었습니다.

이 점이 portproxy를 선택한 가장 큰 이유였습니다.

또한 portproxy는 UDP를 지원하지 않습니다. Microsoft 문서상 protocol로 지원되는 것은 TCP뿐입니다.

따라서 이 방법은:

SSH
HTTP
HTTPS
TCP debug server

같은 TCP service를 노출하기에는 적합하지만 UDP 기반 service까지 일반적인 gateway처럼 forwarding하려는 용도에는 적합하지 않습니다.

Rule 관리

설정 확인:

netsh interface portproxy show all

Rule 삭제:

netsh interface portproxy delete v4tov4 `
    listenaddress=172.16.10.22 `
    listenport=2222

Destination을 변경하고 싶다면 기존 rule을 수정하거나 다시 등록할 수도 있습니다.

이런 형태의 configuration이라는 점 역시 일시적인 SSH tunnel보다 제 use case에는 잘 맞았습니다.

5. Windows에서 가능한 다른 방법들

netsh portproxy만이 Windows에서 가능한 방법은 아닙니다.

몇 가지 다른 선택지도 검토할 수 있습니다.

SSH Jump Host

첫 번째 방법은 처음 사용했던 ProxyJump입니다.

Client
   |
   | SSH authentication
   v
Windows
   |
   | SSH
   v
Target

장점은 매우 단순하다는 것입니다.

추가적인 network configuration도 거의 필요하지 않습니다.

하지만 모든 사용자가 Windows 머신에 로그인할 수 있어야 한다는 문제가 있었습니다.

공용 jump server라면 오히려 좋은 방법이지만, 개인 업무용 Windows laptop을 임시 gateway로 사용하는 제 상황에는 적합하지 않았습니다.

SSH Port Forwarding

두 번째 방법은:

ssh -N -L ...

을 사용하는 방법입니다.

이 방법 역시 매우 간단하고 추가 프로그램도 필요하지 않습니다.

또한 forwarding traffic 자체가 SSH session 안을 통과하기 때문에 encryption이라는 장점도 있습니다.

하지만 forwarding이 SSH session의 lifetime에 종속됩니다.

SSH process 종료
       =
Tunnel 종료

입니다.

Task Scheduler 등을 이용하면 자동화할 수 있지만, 이 경우 결국 persistent SSH process와 reconnect logic을 관리하는 형태가 됩니다.

간단한 임시 tunnel에는 매우 좋은 방식이지만, 차량에 laptop을 계속 놔두고 infrastructure처럼 사용하려는 목적에서는 portproxy 쪽이 더 단순했습니다.

WinNAT

Windows에는 실제 Network Address Translation을 구성할 수 있는 NetNat PowerShell module도 있습니다.

예를 들어:

New-NetNat

으로 NAT instance를 만들 수 있고:

Add-NetNatStaticMapping

으로 static inbound mapping을 추가할 수 있습니다.

Microsoft는 New-NetNat을 packet header의 IP address와 port 정보를 변환하는 NAT object를 만드는 기능으로 설명하고 있으며, Add-NetNatStaticMapping은 external network의 incoming connection을 internal host로 mapping할 수 있습니다.

개념적으로는 제가 처음 portproxy가 동작한다고 생각했던 방식에 더 가깝습니다.

External network
       |
       v
   Windows NAT
       |
       v
Internal network

따라서 두 network 사이에서 Windows를 실제 NAT gateway처럼 운용해야 한다면 훨씬 적절한 도구가 될 수 있습니다.

하지만 제 목적은:

TCP 2222 하나
      ->
Target TCP 22

를 노출하는 것이 전부였습니다.

이를 위해 별도의 NAT object와 internal network topology를 구성하는 것은 필요 이상으로 복잡했습니다.

그래서 이번에는 사용하지 않았습니다.

Internet Connection Sharing

Windows의 Internet Connection Sharing, 즉 ICS를 사용하는 방법도 생각할 수 있습니다.

하지만 ICS의 목적은 한 network connection을 다른 private network의 여러 device와 공유하는 것입니다.

제가 원한 것은 network 전체를 공유하는 것이 아니라 특정 TCP service 하나만 정확하게 노출하는 것이었습니다.

또한 ICS를 사용하면 Windows가 private-side network configuration에 더 적극적으로 관여하게 되기 때문에, 이미 정해진 IP configuration을 사용하는 임베디드 보드 환경에서는 오히려 불필요한 side effect가 생길 수 있습니다.

따라서 이 use case에는 맞지 않았습니다.

RRAS

Windows Server 환경이라면 Routing and Remote Access Service, 즉 RRAS도 선택지가 될 수 있습니다.

RRAS는 Windows machine을 실제 router/VPN/NAT gateway로 운영하기 위한 훨씬 완전한 networking solution입니다.

하지만 차량에 임시로 둔 Windows laptop 하나에서 SSH port 하나를 전달하기 위해 RRAS 수준의 routing infrastructure를 구성하는 것은 지나치게 무거운 해결책입니다.

이 역시 제외했습니다.

별도의 TCP Relay 프로그램

또 다른 방법은 Windows용 TCP relay application을 설치하는 것입니다.

예를 들어 별도의 proxy나 relay daemon이:

listen :2222
     |
     v
connect 192.168.0.10:22

를 수행하도록 만들 수 있습니다.

직접 Python이나 C++로 간단한 TCP relay를 작성하는 것도 어렵지는 않습니다.

하지만 Windows가 이미 같은 목적의 portproxy 기능을 제공하고 있는 상황에서 외부 binary나 별도의 application lifecycle을 추가할 이유가 없었습니다.

그래서 이것도 제외했습니다.

6. 결국 netsh portproxy를 선택한 이유

제가 필요한 조건을 다시 정리하면 다음과 같았습니다.

1. Windows account를 다른 사람과 공유하고 싶지 않다.

2. 사용자는 그냥:
   ssh root@172.16.10.22 -p 2222
   로 접속할 수 있어야 한다.

3. 별도의 SSH tunnel session을 계속 유지하고 싶지 않다.

4. Windows를 완전한 router/NAT gateway로 만들 필요는 없다.

5. SSH라는 TCP service 하나만 forwarding하면 충분하다.

6. 가능하면 Windows 기본 기능만 사용하고 싶다.

이 조건에서는 netsh portproxy가 가장 단순했습니다.

방법 Windows 계정 필요 별도 session/process Network 전체 routing 제 경우
SSH Jump Host 필요 불필요 불필요 △
SSH Tunnel 불필요 필요 불필요 △
netsh portproxy 불필요 불필요 불필요 ✓
WinNAT 불필요 불필요 NAT 구성 필요 과함
ICS 불필요 Windows가 network 공유 구성 Network 단위 부적합
RRAS 불필요 Service Router 구성 지나치게 과함
별도 TCP relay 불필요 별도 process 필요 불필요 불필요

결국 제가 필요했던 것은 router가 아니었습니다.

단순히:

172.16.10.22:2222
        |
        v
192.168.0.10:22

라는 TCP path 하나였습니다.

ProxyJump에서 시작해 SSH tunnel을 거쳐 portproxy까지 오면서 같은 결과를 만드는 방법이 여러 가지라는 것을 확인할 수 있었습니다.

그리고 각각의 방식이 해결하는 문제도 조금씩 달랐습니다.

ProxyJump
    ↓
"중간 머신에 어떻게 로그인할 것인가?"

SSH Tunnel
    ↓
"특정 TCP connection을 어떻게 안전하게 전달할 것인가?"

portproxy
    ↓
"Windows에 특정 TCP forwarding rule을 어떻게 지속적으로 둘 것인가?"

WinNAT / RRAS
    ↓
"Windows를 어떻게 실제 network gateway로 만들 것인가?"

제 경우에는 세 번째 문제를 풀고 있었기 때문에 netsh portproxy가 가장 적절했습니다.
